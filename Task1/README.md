# 1. Стратегия масштабирования и отказоустойчивости

## 1.1 Горизонтальное масштабирование приложений (Kubernetes + HPA)
Все backend-компоненты (core-app, client-info, ins-product-aggregator, ins-comp-settlement) запускаются в Kubernetes и масштабируются горизонтально через HPA, так как:
- рост нагрузки непредсказуем, а горизонтальное масштабирование позволяет быстро добавлять мощности без простоя;  
- проще держать SLO по latency за счёт autoscaling и ограничения ресурсов (`requests/limits`);  
- снижает риск одной ноды как единой точки отказа.

## 1.2 Размещение в нескольких зонах доступности (multi-AZ)
Группы нод распределены по нескольким зонах доступности, реплики сервисов раскладываются по зонам и защищены PDB:  
- отказ одной AZ не приводит к полной недоступности сервиса;  
- помогает уложиться в требование доступности 99,9%.


# 2. Балансировка нагрузки и фейловер

## 2.1 GSLB на входе (geo/latency routing + failover)
Входной трафик (пользовательский и B2B) приходит на GSLB, который распределяет трафик по географии/задержкам и выполняет фейловер по healthcheck:  
- гарантирует переключение трафика на здоровую зону при проблемах;  
- уменьшает влияние деградаций/падений отдельных сегментов;  
- масштабируется лучше, чем одна точка входа.

## 2.2 NGINX Ingress / API Gateway как точка управления трафиком
В каждой зоне входящий трафик принимает NGINX Ingress / API Gateway, выполняет TLS терминацию и маршрутизацию в сервисы Kubernetes:  
- единая управляемая точка для маршрутизации, политик и наблюдаемости;  
- правильное место для последующего внедрения rate-limit и изоляции партнёров.

## 2.3 Health checks на периметре и внутри
Явно выделены проверки:
- `GSLB/LB → Ingress`: `/healthz`  
- `Ingress → Pods`: readiness/liveness probes    
- корректная балансировка и failover возможны только при достоверных health checks;  
- снижает вероятность сбоев, когда трафик отправляется в деградировавшие компоненты.


# 3. Одинаковое время загрузки страниц по регионам

### 3.1 CDN + Object Storage для фронтенда (статический контент)
Статика веб-приложения хранится в Object Storage, раздаётся через CDN:
- скорость загрузки страниц выравнивается по регионам за счёт edge-кеширования;  
- снижает нагрузку на backend (не раздаём статику через сервисы);  
- повышает устойчивость при всплесках трафика (CDN принимает удар).

# 4. Конфигурация базы данных под RTO/RPO

## 4.1 PostgreSQL HA Cluster под Patroni
PostgreSQL развёрнут как HA-кластер (Patroni) на нескольких ВМ/узлах, с репликацией и автоматическим переключением роли primary:
- убираем единую точку отказа;  
- авто-failover позволяет уложиться в RTO <= 45 минут;  
- репликация уменьшает риск потерь данных.

## 4.2 Backups + WAL archive (PITR) в Object Storage
Включены резервные копии и архив WAL для PITR в Object Storage:
- формально и технически закрывает RPO <= 15 минут (через WAL/PITR);  
- позволяет восстановиться после логических ошибок (не только после падений);  
- Object Storage дешевле и надёжнее для долговременного хранения бэкапов.
